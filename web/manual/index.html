Welcome

FES is a small game console that lives on your iPad. You make games for it, called carts, right here: you draw the pictures and write the program that moves them. The programs are written in Lua, a small language that is easy to start with. FES works without a network once it is on your Home Screen, and your carts stay on your iPad. This manual starts with a game you can make in ten minutes, then explains each part in turn.

Your first cart

You will draw a small picture and move it around the screen with the arrow keys. A picture the console can move is called a sprite. Its picture is a tile: a square of 8 by 8 pixels.

  1. Press Carts, then New cart. FES opens the new cart's code.
  2. Press Art, then Sprites. The big square shows the tile picked on the sheet. Tap the first tile, top left on the sheet: that is tile 0. It is empty.
  3. Pick any color except the first one, and draw on tile 0 with your finger. The first color is see-through for sprites, so a tile drawn only in it can't be seen.
  4. Press Code. Replace everything in the editor with this program: 
    x, y = 92, 68
function _update()
  if btn(0) then x = x - 1 end
  if btn(1) then x = x + 1 end
  if btn(2) then y = y - 1 end
  if btn(3) then y = y + 1 end
end
function _draw()
  cls()
  spr(0, x, y)
end
  5. Press Run. Your drawing sits in the middle of the screen. Move it with the D-pad or the arrow keys.
  6. Press Save. The cart now waits for you on the shelf, under Carts.

Here is what the program says. The first line makes two variables, x and y, for where the sprite is. FES calls _update 60 times a second: each btn(n) asks whether button n is held, and the sprite moves one pixel that way. Then FES calls _draw: cls() takes away the sprites placed in the last frame, so the sprite doesn't leave copies of itself behind, and spr(0, x, y) puts tile 0 at x, y. The button numbers are in Buttons.

The console

FES is a pretend console, and like a real one it has fixed limits. Working inside them is part of the fun.

The code editor

The keys along the top of FES are the same in every view.

  • Carts, Code, Art, Game and Help switch between FES's views. Help shows this manual.
  • Run starts the open cart from the beginning and shows Game.
  • Game goes back to the running game without restarting it. If the open cart isn't the one running, because you just opened or restored it, Game runs it.
  • Save keeps the open cart on the shelf. It is hidden while the shelf shows. Set label shows only in Game.
  • The dark strip is the readout: it shows FES's last message, such as Saved My game.
  • The small light at the left is the power light. It is green while a cart runs, and red after an error stops it.

Press Code to write the open cart's program.

Files and tabs

Every cart has main.lua, and FES starts the cart from it. A bigger cart can have more code files, each in its own tab above the editor.

  • New file asks New code file name:. Type a name and press Add, or Cancel. FES makes the name lowercase and adds .lua, so Player becomes player.lua.
  • A name uses a–z, 0–9 and _, doesn't start with a digit, and is at most 32 characters before .lua. A cart holds at most 32 code files. Anything else is refused in the readout with a message that says why, such as Can't add bad-name.lua: code file names use a–z, 0–9 and _, such as player.lua
  • Rename and Delete act on the file in the tab that is showing. They are disabled for main.lua, since the cart starts from it.
  • Another file runs only when require loads it. Renaming a file doesn't change the require calls that name it.
  • With a tab focused, ← and → move between the tabs, and Home and End go to the first and the last.

Errors and where they point

Half a second after you stop typing, FES checks the code for mistakes in how it is written, called syntax errors: the file you see first, then the others. The first one shows under the editor, and its line is marked at the left:

main.lua:3: 'end' expected (to close 'function' at line 1) near <eof>

main.lua:3: means the file main.lua, line 3. Here a function that starts on line 1 never ends: <eof> is the end of the file.

Other mistakes show only when the cart runs. Such an error stops the cart, the power light turns red, and Game shows the whole message with the stack traceback, the list of functions that were running:

main.lua:5: attempt to call a nil value (global 'sprr')
stack traceback:
	main.lua:5: in function '_draw'

Press Code and FES opens the file the error names, puts the cursor on its line and shows the first line of the message under the editor. When something goes wrong explains the messages you are most likely to meet.

Drawing

Press Art to draw the cart's tiles and choose its colors. The sheet shows every tile of one bank. The big square shows the selected tile, large enough to draw on with your finger.

Tiles and banks

A cart has two banks of tiles: Background for the map and Sprites for sprites. Press one to show it. Each bank has 256 tiles, numbered 0 to 255, 16 to a row on the sheet: tile n is in column n % 16 and row n // 16, so tile 17 is in column 1, row 1. Choose a tile by tapping it on the sheet, or with the Tile slider.

Colors and palettes

The console has one main palette of 64 colors. A tile doesn't store colors: each of its pixels stores a color number from 0 to 7. A palette turns those numbers into colors when the tile is drawn. There are 8 background palettes and 8 sprite palettes, each of 8 colors from the main palette, so one tile can be drawn in different colors.

The 8 color swatches in the Art view are colors 0 to 7, the colors you draw with. The drawing color starts at 1. In Sprites, color 0 is see-through and shows as a checkerboard.

The keys 0 to 7 choose the palette the editor shows the tiles in. They change only what you see here: the game chooses each tile's palette when it draws it, with the palette of spr and mset. Try it in the Built-in demo: pressing A while it runs changes the player's palette.

A block is the tiles you edit together, for a picture bigger than one tile. 1×1, 2×2 and 4×4 make it 1, 4 or 16 tiles. The block starts at the selected tile, moved left or up when it would run off the sheet. Paste pastes at the size you copied, with its top-left corner at the selected tile, moved to fit. You can copy in one bank and paste in the other.

Undo and Redo cover every art change: strokes, fills, flips, pastes, palette and main color changes, imports and resets. ⌘ Z and ⇧ ⌘ Z do the same in the Art view. The readout says what changed, such as Undid stroke. or Nothing to undo. Opening a cart, restoring one or making a new one starts a fresh history.

Without a touchscreen, choose a pixel with the Pixel column and Pixel row sliders and press Paint pixel. With Picker or Fill chosen, that key says "Pick color" or "Fill region" instead.

The palette editor

Palettes shows the palette editor for the bank you are in.

  • "Background palettes", or "Sprite palettes", shows the bank's 8 palettes as 8 rows of 8 colors. Tap one to choose that palette and color.
  • Under "Main palette", tap one of the 64 colors to put it in the color you chose.
  • The "Edit main color" field opens iPadOS's color picker and changes that main color itself. Every palette that uses it changes, in both banks.
  • Reset main palette puts back the 64 colors a new cart starts with. It is disabled while nothing has changed.
  • Sprite color 0 can't be changed. The editor says Sprite color 0 is always transparent.

The starting colors are the palette "Z64" by Jehkoba, from Lospec.

Importing a sheet

You can draw a sheet in another app and bring it in. Import sheet and Import sheet and colors each open a file chooser.

  • The picture is a PNG or JPEG of at most 1 MiB. Both sides are multiples of 8, and at most 128 pixels.
  • It replaces all 256 tiles of the bank you are in. Tiles outside the picture become empty.
  • Import sheet keeps the main palette. Every color of the picture must already be in it, and each tile's colors must all be in one of the bank's 8 palettes.
  • Import sheet and colors puts the picture's colors into the main palette from color 0, in the order they first appear, up to 64, and builds the bank's palettes from them. Its question warns that the other bank's tiles may change color too.
  • In a sprite sheet, fully see-through pixels become color 0. A background sheet can't have see-through pixels, and half see-through pixels are refused in both.

When the picture fits, FES asks before replacing anything, for example Replace all 256 sprite tiles with hero.png? Undo puts them back. Press Replace, and the readout says Imported hero.png into the sprite tiles.

When it doesn't, a report titled Can't import hero.png lists every problem and shows the picture with the problem tiles ringed in red. A problem with one tile names it by where it is in the picture:

  • Tile at column 0, row 0 (from pixel 0, 0): 9 colors. A background tile can use 8.
  • The image is 136 × 8 pixels. A sheet is at most 128 × 128.

For a JPEG, the report adds JPEG changes colors slightly when it saves. Export the sheet from your art app as PNG and import that. Press Close to close it.

Carts

Press Carts to see the shelf: the Built-in demo first, then your saved carts, each with its label. Select one to see its label on the big screen.

  • Play opens it and runs it. Edit opens it in Code.
  • With a keyboard, ← and → move along the shelf, Z (A) plays and X (B) edits.
  • New cart opens a new cart named "New cart", with a short program to start from and blank art.
  • Duplicate saves a copy of the selected cart named "… copy". It copies the cart as last saved, without changes you haven't saved.
  • Delete asks Delete My game? This can't be undone. Export it first if you want a backup. If you delete the open cart, the demo opens.

The demo can't be duplicated, exported or deleted. To make your own copy, Edit it, type a new name under Cart name and Save.

Opening another cart, with Play, Edit or New cart, first asks Discard unsaved changes to My game? if the open cart has changes you haven't saved. Discard throws them away, and Cancel keeps them.

Saving

Save keeps the open cart under the name in the Cart name field, and the readout says Saved My game. Change the name and Save to rename the cart. A name can't be empty or longer than 64 characters: Can't save: the name is empty.

Labels

A cart's label is the picture on its cartridge. Run the cart, and when the screen shows what you want, press Set label. The readout says Label set. Save to keep it.

Unsaved changes after a restart

Every change you make writes a recovery copy of the open cart's unsaved changes into the browser's storage. If FES closes before you save, because you closed the tab, iPadOS stopped it, or a cart froze it, the next start asks Restore unsaved changes to My game?

  • Restore opens the changes in Code. They are still unsaved, so Save them.
  • Discard deletes the recovery copy.

There is only one recovery copy, for the open cart. It is not a backup: Keeping your carts safe is.

Keeping your carts safe

Your carts live in FES's storage in Safari, on this iPad. Nothing copies them anywhere else.

Add FES to your Home Screen

Safari deletes a website's stored data after 7 days of using Safari without visiting that site, and your carts are that data. FES on the Home Screen doesn't count Safari's days: WebKit, Safari's engine, says Home Screen web apps "have their own counter of days of use", and it doesn't expect their data to be deleted (WebKit's post).

To add FES, open Safari's Share menu, then choose Add to Home Screen. The note about this at the top of FES goes away for 7 days when you press Not now.

FES on the Home Screen keeps its own carts, apart from the ones in Safari. To move carts there, Export them in Safari and Import them in the Home Screen FES.

Export and import

  • Export on the shelf writes the selected cart to a .fes file, as it was last saved, so Save first. In the Home Screen FES it opens the Share sheet: choose Save to Files. In a Safari tab, Safari downloads the file. The readout says Exported My game.fes.
  • Import on the shelf opens Files. The cart you choose is added as a new cart, even if one has the same name: Imported My game as a new cart.

Export your carts now and then, and keep the files in iCloud Drive or on another device.

What is in a .fes

A .fes file is a zip of text files, so you can unzip it and read them: cart.json with the cart's name, main.lua and the other code files, background.tiles, sprites.tiles, palettes.pal, main-palette.hex, map.map, and label.hex when the cart has a label. FES doesn't read a zip made by Files' Compress: … is compressed; FES reads .fes files it exported.

Lua in ten minutes

This is the part of Lua you need to start. Try each piece in a cart: the screen shows nothing, but a mistake stops the cart with a message that says what went wrong.

Comments

Two dashes start a comment. Lua skips everything after them to the end of the line.

-- the player starts in the middle
x = 92

Variables

A variable is a name for a value. Give it a value with =. A variable you never gave a value is nil, which means "nothing".

A variable made without local is global: every function in every file of the cart can see and change it. A variable made with local exists only inside the block (function, loop, if or file) where you made it. Prefer local: no other part of the cart can change it by accident, and two files can use the same name without clashing.

score = 0        -- global
local speed = 2  -- local to this file
local x, y = 92, 68

Numbers

+, - and * work as you expect. Division needs care:

  • / always gives a number with a fraction: 7 / 2 is 3.5, and 6 / 2 is 3.0.
  • // divides and rounds down to a whole number: 7 // 2 is 3, and -7 // 2 is -4. Use it to turn a pixel position into a map cell, as in x // 8.
  • % is what is left over: 7 % 2 is 1. (i + 1) % 8 counts 0 to 7 and starts again.

Strings

Text goes in quotes, "like this". Join two strings with ..: "score: " .. score. A number joins as its digits.

Tables

A table holds many values. Used as a list, it counts from 1, not 0, and # gives its length.

local tiles = {0, 1, 1, 0}
local first = tiles[1]  -- 0
local count = #tiles    -- 4
tiles[#tiles + 1] = 1   -- adds a fifth

Used as a record, it holds named fields. p.x is the field x of p.

local p = { x = 92, y = 68 }
p.x = p.x + 1

Functions

A function is a piece of code with a name, which runs when you call it. return hands a value back to the caller.

local function middle(a, b)
  return (a + b) // 2
end
local x = middle(0, 184)  -- 92

If

== asks "is equal", ~= asks "is not equal". and, or and not combine questions.

if lives == 0 then
  over = true
elseif lives ~= 3 then
  hurt = true
else
  hurt = false
end

Only nil and false count as false. Everything else is true, even 0, which surprises people who know other languages. See Rules for every call.

Loops

A numeric for counts from the first number to the last, both included. for … in ipairs goes through a list in order, and for … in pairs goes through every field of a table in no particular order. while repeats as long as its question is true.

local tiles = {0, 1, 1, 0}
local p = { x = 92, y = 68 }
local total = 0
local x = 40
for column = 0, 31 do
  mset(column, 0, 1)
end
for i, tile in ipairs(tiles) do
  mset(i, 1, tile)
end
for name, value in pairs(p) do
  total = total + value
end
while x > 0 do
  x = x - 8
end

What FES leaves out

Carts run in a sandbox: the part of Lua that can't harm your iPad or freeze FES.

  • Available: Lua's basic functions, such as pairs, tostring and pcall, and the libraries string, table, math, utf8 and coroutine.
  • Not available: print, io, os, debug, package, dofile, loadfile, warn and string.dump.
  • load takes Lua text only, not compiled code, and setmetatable refuses a __gc field (Budgets and errors).

There is no print yet. To see a value while you work, stop the cart with it: error("x is " .. tostring(x)) stops the cart with a message that includes x is 92.

The rest of Lua is in its reference manual, and every function is listed in its index.

API reference

The API is the set of functions your cart calls to work the console: to place sprites, read the buttons, change the map and move the camera. It works the other way too: FES calls your cart's _init once when the cart starts, then _update and _draw every frame.

The examples show sprite tile 0 and background tiles 0 and 1. A new cart's tiles are empty, so draw on those three first, as in Your first cart: sprite tile 0 under Art, Sprites, and background tiles 0 and 1 under Art, Background.

  • cls takes away the sprites.
  • spr places a sprite.
  • btn asks whether a button is held.
  • btnp asks whether a button was just pressed.
  • mset puts a tile on the map.
  • mget reads a tile from the map.
  • camera scrolls the view.
  • require runs another file of the cart.

Rules for every call

  • Where a call wants a number, it takes a Lua number or a string of digits, such as "5". Anything else stops the cart: main.lua:12: bad argument #1 to 'spr' (number expected, got string). A missing number says got no value.
  • NaN and infinity, which you get from 0 / 0 and 1 / 0, stop the cart too: bad argument #2 to 'spr' (finite number expected). Only btn and btnp answer false for them instead.
  • Numbers are rounded down to a whole number: 1.9 is 1 and -0.5 is -1. Keep fractions in your own variables, and they add up: x = x + 0.5 moves a sprite one pixel every other frame.
  • Every number passes through a float on its way in, so whole numbers bigger than 253 or smaller than -253 aren't exact: spr(math.maxinteger, 0, 0) shows tile 0, not tile 255.
  • A number outside its range wraps around instead of stopping the cart, the way a car's odometer goes from 999999 back to 0. Tile 256 is tile 0, and tile -1 is tile 255.
    What the number isRange
    Sprite position-32768 to 32767
    Tile0 to 255
    Palette0 to 7
    Map cell, column or row0 to 31
  • Flips and behind take true, false or nil, and nothing else. In Lua 0 counts as true, so spr(n, x, y, 0, 1) stops the cart instead of flipping the sprite when you didn't mean it.
  • An argument shown in [brackets] is optional: leave it out, or pass nil to skip it and give the next one. Extra arguments are ignored.
  • A mistake in a call stops the cart like any Lua error, unless you catch it with pcall.

When things show

The calls don't draw anything themselves. They change the console's parts, and FES draws the picture from them after _draw returns.

  • The console keeps its sprites in a sprite table of 64 entries. Each spr fills the next free entry, in the order you call it, and the first spr of a frame is in front of the others. Once all 64 are used, more spr calls do nothing until cls().
  • A sprite drawn behind is behind the map and behind every sprite that isn't, whichever spr came first. The map hides it everywhere except where the map shows color 0 of its palette. In every sprite, color 0 is see-through.
  • Sprites stay in the table from frame to frame until cls(). Call cls() at the start of _draw and place every sprite again each frame, or place sprites once in _init and leave them.
  • At most 16 sprites show on any one scanline; on that row, the ones later in the table are left out. Only sprites with at least one column on screen count, even if that column is see-through, so sprites waiting fully off the left or right edge don't use up the row.
  • camera(x, y) scrolls the map and shifts every later spr. The map uses the camera as it is when the frame is drawn; each sprite uses the camera as it was when its spr ran.
  • So camera() in the middle of _draw also scrolls the map back to 0, 0. Until FES gets a layer for scores and menus, draw those sprites with the camera still set, at cx + x, cy + y, where cx, cy is the camera position.
  • The map repeats every 256 pixels in both directions. Sprites don't repeat.

Budgets and errors

So that one cart can't freeze FES, each cart gets a budget. These numbers may still change.

  • Each frame, _update and _draw together may run 500,000 Lua instructions. When the cart starts, the top level of main.lua, the files it requires, and _init together get the same again. Going over stops the cart with main.lua:N: CPU budget exceeded, where N is the line it got to.
  • The cart's Lua values may take up to 8 MiB of memory. Going over stops the cart with memory budget exceeded.
  • A function that calls itself too deep, usually one that never stops, stops the cart with stack overflow.
For the curious: how the budget can't be dodged
  • pcall can't catch CPU budget exceeded: the next function call, or the next 1,000 instructions, raise it again. If _update, _draw, _init or the top of main.lua finishes with the budget spent, for example through return pcall(f) or a coroutine.resume whose coroutine ran out, the cart stops with CPU budget exceeded and no line.
  • Once the budget is spent, xpcall doesn't call its message handler. It returns false and the budget error unchanged, and the cart stops at its next function call, within 1,000 instructions, or when its callback returns.
  • A frame that takes longer than 250 milliseconds counts as over budget, even if it ran few instructions, so library calls on large data in a loop can't freeze the console.
  • When memory runs out, pcall sees not enough memory. If nothing catches it, the cart stops with memory budget exceeded and no line.
  • Lua stops counting instructions while a __gc metamethod runs, so a loop in one could freeze the console. setmetatable stops the cart with main.lua:N: __gc metamethods are not allowed for a metatable with a __gc field. Adding __gc to a metatable after setmetatable does nothing, as in standard Lua.

cls

cls()

Takes away every sprite, so the next spr fills the first entry of the sprite table again.

Takes no arguments. The map stays as it is. Returns nothing.

local x = 0
function _update() x = (x + 1) % 192 end
function _draw()
  cls()
  spr(0, x, 68)
end

Common mistakes

  • Leaving cls() out of _draw. The sprites of earlier frames stay, so a moving sprite leaves a trail of copies, and after 64 frames the table is full and it stops moving.
  • Passing a color, as in PICO-8's cls(1). FES ignores it, so cls(1) does the same as cls(). The map is always behind the sprites; change it with mset.

spr

spr(n, x, y, [palette], [flip_x], [flip_y], [behind])

Places sprite tile n on the screen with its top-left corner at x, y.

NameMeaningRangeDefault
nWhich sprite tile to show, from Art, Sprites0 to 255required

yTop edge in pixels. The camera's y is taken off it.-32768 to 32767, after the camera is taken offrequired

local x = 0
function _update() x = (x + 1) % 192 end
function _draw()
  cls()
  spr(0, x, 60)
  spr(0, 184 - x, 76, 0, true)
end

Common mistakes

  • Flipping with numbers: spr(n, x, y, 0, 1) stops the cart with bad argument #5 to 'spr' (boolean expected, got number). Write spr(n, x, y, 0, true).
  • Using a background tile's number. n picks from the sprite tiles, which are separate from the background tiles that mset uses: sprite tile 3 and background tile 3 are different pictures.

btn

btn(i)

Tells whether button i is held down.

NameMeaningRangeDefault
iThe button's number, from Buttons0 to 7; any other number gives falserequired

Returns true while the button is held, and false otherwise. i is rounded down like every number, so btn(4.7) asks about A and btn(-0.5) is false. A string of digits such as "4" works too.

local x = 92
function _update()
  if btn(0) then x = x - 1 end
  if btn(1) then x = x + 1 end
end
function _draw() cls() spr(0, x, 68) end

Common mistakes

  • Leaving out the number: btn() stops the cart with bad argument #1 to 'btn' (number expected, got no value). Something that isn't a number stops it too: btn(true) gives bad argument #1 to 'btn' (number expected, got boolean).
  • Using btn for something that should happen once per press, such as a jump. btn stays true every frame the button is held; use btnp.

btnp

btnp(i)

Tells whether button i went down this frame.

NameMeaningRangeDefault
iThe button's number, from Buttons0 to 7; any other number gives falserequired

Returns true only on the first frame the button is held, and false otherwise. i works as in btn.

local palette = 0
function _update()
  if btnp(4) then palette = (palette + 1) % 8 end
end
function _draw() cls() spr(0, 92, 68, palette) end

Common mistakes

  • Expecting it to repeat while the button stays down, as PICO-8's btnp does after a moment. In FES it is true once per press; to repeat, count frames yourself while btn is true.

mset

Puts a background tile in one cell of the map.

NameMeaningRangeDefault

function _init()

end

Common mistakes

  • Passing a position in pixels. x and y count cells, so divide pixels by 8: mset(px // 8, py // 8, 1).
  • Using a sprite tile's number. tile picks from the background tiles, which are separate from the sprite tiles that spr uses.

mget

mget(x, y)

Tells which tile and palette are in one cell of the map.

NameMeaningRangeDefault
xThe cell's column. A cell is 8 by 8 pixels.0 to 31required
yThe cell's row0 to 31required

Returns two whole numbers: the background tile (0 to 255) and its palette (0 to 7). local t = mget(x, y) keeps only the tile. The cells wrap around like the map on screen, so mget(32, 0) reads cell 0, 0.

local x, y = 40, 64
function _init() mset(12, 8, 1) end
function _update()
  if btn(1) and mget((x + 8) // 8, y // 8) ~= 1 then x = x + 1 end
  if btn(0) then x = x - 1 end
end
function _draw() cls() spr(0, x, y) end

The sprite walks right until background tile 1 is in its way.

Common mistakes

  • Passing a position in pixels. Divide by 8 first: mget(px // 8, py // 8).

camera

camera([x], [y])

Scrolls the view so that the point x, y of the map is at the top-left corner of the screen.

NameMeaningRangeDefault
xHow far right to scroll, in pixelsAny number; it wraps around every 65536, and the map repeats every 2560
yHow far down to scroll, in pixelsAny number; it wraps around every 65536, and the map repeats every 2560

Returns nothing. camera() goes back to 0, 0. Every spr after it is shifted too, so sprites and the map stay together. When things show explains when each one uses the camera.

local x = 92
function _init() mset(16, 9, 1) end
function _update() if btn(1) then x = x + 1 end end
function _draw()
  cls()
  camera(x - 92, 0)
  spr(0, x, 68)
end

The sprite stays in the middle of the screen while the map moves past it.

Common mistakes

  • Calling camera() in the middle of _draw to place a score. It scrolls the map back to 0, 0 too; see When things show.
  • Calling camera after spr. Only the sprites placed after it are shifted.

require

require(name)

Runs another code file of the cart and gives back what that file returns.

NameMeaningRangeDefault
nameThe file's name without .lua: "player" runs player.luaA string; a number is turned into onerequired

Returns what the file returns, or true if it returns nothing. Only the first require of a name runs the file; later ones give back the same value without running it again. The file receives name as ....

A cart starts from main.lua. Its other code files run only when something requires them.

  • Globals are shared between files, and a file's local variables are its own. To share functions without making globals, return a table of them.
  • Errors name the file they happen in: player.lua:12: attempt to index a nil value.
  • A required file runs inside the budget of whatever called require, usually the top of main.lua and _init.
  • Renaming a file doesn't change the require calls that name it. Change them yourself.
-- main.lua
local player = require("player")
function _update() player.update() end
function _draw() cls() player.draw() end
-- player.lua
local player = { x = 92, y = 68 }
function player.update()
  if btn(1) then player.x = player.x + 1 end
end
function player.draw() spr(0, player.x, player.y) end
return player

Common mistakes

  • Adding .lua: require("player.lua") looks for player.lua.lua and stops the cart with module 'player.lua' not found: this cart has no file player.lua.lua. A misspelled name stops it the same way: main.lua:3: module 'plyer' not found: this cart has no file plyer.lua.
  • Requiring main: module 'main' can't be required: the cart starts from main.lua.
  • Leaving out the name: require() stops the cart with bad argument #1 to 'require' (string expected, got no value).
  • Two files that require each other while they load: the cart stops with module 'enemy' is still loading (circular require). Move what they share to a third file, or call require inside a function that runs later.

One quirk: if a file's top level stops with an error that the cart catches with pcall, requiring that file again says still loading (circular require) instead of running it again.

Move a sprite

The program from Your first cart, finished: the sprite moves with the D-pad and can't leave the screen.

local x, y = 92, 68
function _update()
  if btn(0) then x = x - 1 end
  if btn(1) then x = x + 1 end
  if btn(2) then y = y - 1 end
  if btn(3) then y = y + 1 end
  x = math.max(0, math.min(x, 184))
  y = math.max(0, math.min(y, 136))
end
function _draw()
  cls()
  spr(0, x, y, 7)
end

Lines worth noticing

  • local x, y keeps the position to this file, as Lua in ten minutes recommends.
  • math.max(0, math.min(x, 184)) keeps x between 0 and 184. The screen is 192 pixels wide and a sprite is 8, so 184 is the last place where the whole sprite shows. The screen is 144 high, so y stops at 136.
  • spr(0, x, y, 7) colors the sprite with sprite palette 7, the demo's player colors.

Animation

The player walks: while it moves, it switches between sprite tiles 0 and 1 every 8 frames, and it faces the way it last went.

local x, y = 92, 68
local t = 0
local tile = 0
local facing_left = false

function _update()
  local dx, dy = 0, 0
  if btn(0) then dx = -1 end
  if btn(1) then dx = 1 end
  if btn(2) then dy = -1 end
  if btn(3) then dy = 1 end
  if dx ~= 0 then facing_left = dx < 0 end
  x = math.max(0, math.min(x + dx, 184))
  y = math.max(0, math.min(y + dy, 136))
  if dx ~= 0 or dy ~= 0 then
    t = t + 1
    tile = (t // 8) % 2
  else
    tile = 0
  end
end

function _draw()
  cls()
  spr(tile, x, y, 7, facing_left)
end

Lines worth noticing

  • t counts the frames spent walking. t // 8 goes up by one every 8 frames, and % 2 turns that into 0, 1, 0, 1. So tile changes 7 or 8 times a second. // and % are in Lua in ten minutes.
  • Standing still shows tile 0, so the player stops on both feet.
  • facing_left changes only when dx isn't 0, so going up or down keeps the way the player faces. Passing it to spr mirrors the tile, so one picture faces both ways.

A room with walls

The cart builds a room that fills the screen, 24 by 18 cells, and the player can't walk through its walls. It slides along a wall when pressing against it at a slant.

local floor, wall = 0, 1
local x, y = 16, 16

function _init()
  for cy = 0, 17 do
    for cx = 0, 23 do
      local edge = cx == 0 or cy == 0 or cx == 23 or cy == 17
      local inner = (cx == 8 and cy < 12) or (cy == 10 and cx > 14)
      if edge or inner then
        mset(cx, cy, wall, 4)
      else
        mset(cx, cy, floor, 2)
      end
    end
  end
end

local function is_wall_at(px, py)
  return mget(px // 8, py // 8) == wall
end

local function is_blocked(px, py)
  return is_wall_at(px, py) or is_wall_at(px + 7, py)
    or is_wall_at(px, py + 7) or is_wall_at(px + 7, py + 7)
end

function _update()
  local dx, dy = 0, 0
  if btn(0) then dx = -1 end
  if btn(1) then dx = 1 end
  if btn(2) then dy = -1 end
  if btn(3) then dy = 1 end
  if not is_blocked(x + dx, y) then x = x + dx end
  if not is_blocked(x, y + dy) then y = y + dy end
end

function _draw()
  cls()
  spr(0, x, y, 7)
end

Lines worth noticing

  • _init runs once, so the map is built once. mset(cx, cy, wall, 4) puts the wall tile with background palette 4 in one cell.
  • is_wall_at turns a pixel into a cell with // 8 and asks mget what is there. mget gives the tile and its palette, and == compares only the tile.
  • is_blocked checks all four corners of the sprite, px + 7 being its right edge, so no part of it can enter a wall.
  • The cart tries the move across and the move down separately. When one is blocked, the other still happens, which is what lets the player slide along a wall.

A camera that follows the player

The map is 32 by 32 cells, 256 pixels each way, bigger than the screen. The camera keeps the player in the middle of the screen and stops at the map's edges.

local x, y = 88, 64

local function clamp(value, low, high)
  return math.max(low, math.min(value, high))
end

function _init()
  for cy = 0, 31 do
    for cx = 0, 31 do
      local edge = cx == 0 or cy == 0 or cx == 31 or cy == 31
      local pillar = cx % 6 == 3 and cy % 6 == 3
      if edge or pillar then
        mset(cx, cy, 1, 4)
      else
        mset(cx, cy, 0, 2)
      end
    end
  end
end

function _update()
  if btn(0) then x = x - 1 end
  if btn(1) then x = x + 1 end
  if btn(2) then y = y - 1 end
  if btn(3) then y = y + 1 end
  x = clamp(x, 8, 240)
  y = clamp(y, 8, 240)
end

function _draw()
  cls()
  local cam_x = clamp(x + 4 - 96, 0, 64)
  local cam_y = clamp(y + 4 - 72, 0, 112)
  camera(cam_x, cam_y)
  spr(0, x, y, 7)
end

Lines worth noticing

  • x and y are positions on the map, not on the screen. Clamping them to 8 and 240 keeps the player inside the border walls. The player walks over the pillars: A room with walls shows how to stop at them.
  • x + 4 - 96 puts the middle of the sprite (4 pixels in) at the middle of the screen (96 pixels across). The camera stops at 0 and at 64, which is the map's 256 pixels minus the screen's 192. Down, it stops at 112, 256 minus 144.
  • camera comes before spr: only sprites placed after it are shifted, as When things show explains.

Many sprites, and the limits

This cart runs into the console's two sprite limits on purpose. It starts with 20 sprites in a row. Press → to add 8 and ← to take 8 away, up to 80.

local count = 20

function _update()
  if btnp(1) then count = count + 8 end
  if btnp(0) then count = count - 8 end
  count = math.max(0, math.min(count, 80))
end

function _draw()
  cls()
  for i = 0, count - 1 do
    local column = i % 20
    local row = i // 20
    spr(0, 6 + column * 9, 20 + row * 12, 7)
  end
end

What you see:

  • Each row shows only 16 sprites, and its last 4 are missing. At most 16 sprites show on one scanline, one row of pixels across the screen, and the first 16 placed win. The rows are 12 pixels apart and a sprite is 8 high, so no two rows share a scanline and each row has its own 16.
  • The sprite table has 64 entries, filled in the order of the spr calls. The first three rows take 60, so the fourth row gets 4 and no more: once all 64 are used, more spr calls do nothing until the next cls().
  • A sprite takes a table entry even when it is off the screen.
  • A sprite uses up one of a scanline's 16 if it covers that scanline and has any column on the screen, even a see-through one. The demo's sprite tile 0 has a see-through left column, so spr(0, 191, y) shows nothing but still counts on its rows. A sprite fully off the left or right edge, at x of -8 or less, or 192 or more, doesn't count.

Lines worth noticing

  • btnp is true only on the frame a button goes down, so each press adds 8 once, however long it is held.
  • i % 20 is the column and i // 20 the row, so the sprites fill the rows in order. The full rules are in When things show.

Two files

As a cart grows, split it into files. Here main.lua builds the floor and runs the frame, and player.lua holds everything about the player. To add player.lua, press New file in the Code view and name it player.lua.

local player = require("player")

function _init()
  for cy = 0, 17 do
    for cx = 0, 23 do
      mset(cx, cy, 0, 2)
    end
  end
end

function _update()
  player.update()
end

function _draw()
  cls()
  player.draw()
end
local x, y = 92, 68
local facing_left = false

local player = {}

function player.update()
  if btn(0) then
    x = x - 1
    facing_left = true
  end
  if btn(1) then
    x = x + 1
    facing_left = false
  end
  if btn(2) then y = y - 1 end
  if btn(3) then y = y + 1 end
end

function player.draw()
  spr(0, x, y, 7, facing_left)
end

return player

Lines worth noticing

  • require("player") takes the file's name without .lua. It runs player.lua once and gives back what that file returns. More is in require.
  • x, y and facing_left are local to player.lua: main.lua can't see or change them. Only the table player, which the file returns, is shared.
  • player.update and player.draw are functions stored in that table, so main.lua calls them through the name it gave the result of require.

When something goes wrong

An error stops the cart and shows its message on the screen. main.lua:4: at the start means the file main.lua, line 4, and Code takes you there (The code editor). These are the messages you are most likely to meet.

CPU budget exceeded

main.lua:2: CPU budget exceeded means the cart did too much work in one frame, usually in a loop that never ends. Look at the loop on that line and check that it stops. Sometimes the message has no line. The limits are in Budgets and errors.

memory budget exceeded

The cart's values took more memory than it is allowed. It comes without a line. Usually a table grows every frame and nothing ever empties it: look for t[#t + 1] = … in _update or _draw.

attempt to call a nil value

main.lua:5: attempt to call a nil value (global 'sprr') means the cart called a function that doesn't exist. Check the spelling, and the case: Spr isn't spr. A function from another file needs require first. A function in a table shows as (field 'update').

module … not found

main.lua:1: module 'plyer' not found: this cart has no file plyer.lua means require names a file the cart doesn't have. Check the name, and that you added the file. Write require("player"), without .lua. require("main") gives module 'main' can't be required: the cart starts from main.lua.

A syntax error

main.lua:3: 'end' expected (to close 'function' at line 1) near <eof> shows under the code before the cart runs. Something isn't written the way Lua expects, here a missing end. The line number is where Lua noticed, which can be after the real mistake.

A damaged cart

A cart file that can't be read is damaged. A save that was cut off partway can cause it.

  • A cart shown on the shelf as "Damaged cart" says, when you select it, This cart's cart.json is missing or can't be read, so it can only be deleted.
  • Any other broken file shows when you Play or Edit the cart, such as Can't load: sprites.tiles line 3: expected 128 digits, found 2
  • Import refuses a broken file with Can't import my-game.fes: …, and a file from a newer FES with Can't import my-game.fes: cart.json: This cart was made with a newer FES (format 9); this FES reads format 4.

What to do: import your last export of the cart, then delete the damaged one.

Saving is unavailable (Private Browsing?)

FES says this when it starts if it can't use the browser's storage, usually because the tab is in Private Browsing. Save and Import are disabled, so nothing you make can be kept. Open FES in a normal tab or from the Home Screen.
