# 012 CPU and memory budgets
Status: accepted (2026-10-31, T11)
Context: SPEC asks for an instruction-count hook per frame and a capped allocator passed to lua_newstate, both ending the cart with an on-screen error, but leaves the numbers open. T09 QA found that a __call cycle hangs inside one VM instruction, where a count hook never fires, and that string.rep("x", 2e9) grew wasm memory past 2 GB. Decision 010 requires that allocations outside a protected call never fail on the cap.
Decision: The limits are placeholders in Runtime's Budgets enum (500,000 instructions, 8 MiB; docs/DEBT.md). The main chunk and _init share one instruction budget, and _update and _draw share one per frame. A count hook charges a meter every 1000 instructions instead of using the hook counter as the budget, because each coroutine keeps its own counter, inherited at creation and never reset. The meter is reached through lua_getallocf's ud, so the hook needs no cart reference before lua_error longjmps out of it (decision 011). Once the budget is spent, the hook re-arms itself with count 1 and raises "main.lua:N: CPU budget exceeded" (luaL_where level 0, the interrupted function), so pcall cannot swallow it: the next instruction raises again. The allocator is our lua_Alloc over libc realloc/free with a BudgetMeter as ud. It counts every byte Lua allocates and refuses growth past the cap before calling realloc, so wasm memory never grows for a refused request; Lua's emergency GC retries once, so the cap limits live data. Sizes are read as UInt(bitPattern:) because size_t imports as Int and a wasm32 request over 2 GiB would look negative. The cap is enforced only around luaL_loadbufferx and lua_pcallk; setup, callback lookup, reading the error and lua_close allocate uncapped. Lua does not call the message handler for memory errors, so LUA_ERRMEM is shown as "memory budget exceeded" with no line; memory errors stay catchable by pcall, as in standard Lua. A __call chain is resolved in luaD_precall without running an instruction, and each step grows the stack by one slot and copies the frame, so in stock 5.4.9 it costs O(n^2) up to LUAI_MAXSTACK (1,000,000): hours. Sources/CLua/fes_lua_user.h, included through Lua's LUA_USER_H hook so the vendored files stay unmodified (decision 001), sets LUAI_MAXSTACK to 15,000, luaconf.h's own value for 16-bit-int platforms: the cycle ends with "stack overflow" in about 100 ms in WebKit, and Lua recursion still reaches about 1,500 levels for a function with 10 locals and temporaries, 7,500 for a tiny one. Swift must use the same value for LUA_REGISTRYINDEX: Runtime gets the define through -Xcc, because SwiftPM does not pass cSettings to importers, and reads FES_LUA_STACK_SLOTS, because Swift's importer keeps luaconf.h's LUAI_MAXSTACK despite the #undef.
Alternatives: the hook count as the whole budget, reset with lua_sethook each frame (coroutines would keep stale counters or get a fresh budget each); raising once (pcall in a loop swallows it); luaL_error in the hook (names the caller's line); luaL_newstate plus lua_setallocf around Lua's own allocator (the state's first blocks go uncounted and underflow the counter when freed); Swift's allocate (traps instead of returning nil); a memory error with a line raised later from the hook (one huge allocation must be refused at once); wrapping setmetatable to reject __call cycles (metatables change after the call); editing luaconf.h (decision 001); a wall-clock limit (synchronous wasm on the main thread cannot be interrupted). Still open: a single C library call such as backtracking string.find can run for minutes with no instruction executed, and Lua turns hooks off inside __gc finalizers and inside the hook itself, so an endless finalizer, or an endless xpcall handler called for the hook's own error, is never charged; only a console in a Worker that the page can terminate would bound all of them.
