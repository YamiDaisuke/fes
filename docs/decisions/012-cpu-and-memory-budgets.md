# 012 CPU and memory budgets
Status: accepted (2026-10-31, T11)
Context: SPEC asks for an instruction-count hook per frame and a capped allocator passed to lua_newstate, both ending the cart with an on-screen error, but leaves the numbers open. T09 QA found that a __call cycle hangs inside one VM instruction, where a count hook never fires, and that string.rep("x", 2e9) grew wasm memory past 2 GB. Decision 010 requires that allocations outside a protected call never fail on the cap.
Decision: The limits are placeholders in Runtime's Budgets enum (500,000 instructions, 8 MiB; docs/DEBT.md). The main chunk and _init share one instruction budget, and _update and _draw share one per frame. A count hook charges a meter every 1000 instructions instead of using the hook counter as the budget, because each coroutine keeps its own counter, inherited at creation and never reset. The meter is reached through lua_getallocf's ud, so the hook needs no cart reference before lua_error longjmps out of it (decision 011). The hook is set once, before the main chunk, for count and call events; coroutines inherit it at creation and it never changes, so no hook state carries into the next frame. Count events charge the meter, and every event raises "main.lua:N: CPU budget exceeded" while the meter is spent (luaL_where level 0 for count events, the interrupted function; level 1 for call events, which fire before the callee runs, so the line is the caller's; when that level is C, as when string.rep calls its buffer's __close, the hook uses the nearest level up that has a line). So pcall cannot swallow it: the next call, or the next 1000 instructions, raise again. A tail call to a C function, as in `return pcall(f)`, or one coroutine.resume that catches the error, can return with no further event, so a lua_pcallk that returns LUA_OK with the meter spent stops the cart with "CPU budget exceeded" and no line. One instruction can start C work of any size: a loop of string.rep, table.concat, table.sort or table.insert(t, 1, x) runs few instructions but took up to 38.7 s in WebKit (T11 QA). So each budget period also has a wall-clock deadline, 250 ms (placeholder): every 16th hook event reads ContinuousClock and, past the deadline, spends the rest of the instruction budget, so the same error, end-of-call check and xpcall guard apply. Reading the clock goes through the WASI shim's clock_time_get, which builds a BigInt and a DataView per read, so it is not done on every event. The instruction count stays the deterministic limit; a cart under it reaches the deadline only in a frame that already takes 250 ms. The allocator is our lua_Alloc over libc realloc/free with a BudgetMeter as ud. It counts every byte Lua allocates and refuses growth past the cap before calling realloc, so wasm memory never grows for a refused request; Lua's emergency GC retries once, so the cap limits live data. Sizes are read as UInt(bitPattern:) because size_t imports as Int and a wasm32 request over 2 GiB would look negative. The cap is enforced only around luaL_loadbufferx and lua_pcallk; setup, callback lookup, reading the error and lua_close allocate uncapped. Lua does not call the message handler for memory errors, so LUA_ERRMEM is shown as "memory budget exceeded" with no line; memory errors stay catchable by pcall, as in standard Lua. A __call chain is resolved in luaD_precall without running an instruction, and each step grows the stack by one slot and copies the frame, so in stock 5.4.9 it costs O(n^2) up to LUAI_MAXSTACK (1,000,000): hours. Sources/CLua/fes_lua_user.h, included through Lua's LUA_USER_H hook so the vendored files stay unmodified (decision 001), sets LUAI_MAXSTACK to 15,000, luaconf.h's own value for 16-bit-int platforms: the cycle ends with "stack overflow" in about 100 ms in WebKit, and Lua recursion still reaches about 1,500 levels for a function with 10 locals and temporaries, 7,500 for a tiny one. Swift must use the same value for LUA_REGISTRYINDEX: Runtime gets the define through -Xcc, because SwiftPM does not pass cSettings to importers, and reads FES_LUA_STACK_SLOTS, because Swift's importer keeps luaconf.h's LUAI_MAXSTACK despite the #undef. Lua turns hooks off inside __gc finalizers and inside the hook itself, so code running there is never charged. The sandbox's setmetatable therefore refuses a metatable with any non-nil __gc field, checked raw as Lua does, with "main.lua:N: __gc metamethods are not allowed"; Lua marks an object for finalization only inside setmetatable, and only if __gc is non-nil then, so a __gc added later never runs, and a placeholder such as __gc = false, which could be swapped for a function later, is refused too. The sandbox's xpcall replaces the cart's message handler with a C closure that calls it only while instructions are left, and otherwise returns the message unchanged: the handler for the hook's own error would run unhooked, and a handler entered earlier that loops ends with the hook's error. It then calls Lua's own xpcall, so yields and results are unchanged. The closure's Swift frame holds only plain values when the cart's handler longjmps through it (decision 011).
Alternatives: the hook count as the whole budget, reset with lua_sethook each frame (coroutines would keep stale counters or get a fresh budget each); raising once (pcall in a loop swallows it); luaL_error in the hook (names the caller's line); luaL_newstate plus lua_setallocf around Lua's own allocator (the state's first blocks go uncounted and underflow the counter when freed); Swift's allocate (traps instead of returning nil); a memory error with a line raised later from the hook (one huge allocation must be refused at once); wrapping setmetatable to reject __call cycles (metatables change after the call); editing luaconf.h (decision 001); a wall-clock limit enforced from outside the VM (synchronous wasm on the main thread cannot be interrupted; the deadline is only read inside the hook); leaving the __gc and xpcall-handler freezes to a Worker (the owner chose to restrict carts now); refusing only function-valued __gc (a placeholder swapped later still finalizes); re-arming the count hook to 1 instruction once the budget is spent (a tail call to a C function returns without another instruction, and the main thread kept the count-1 hook into the next frame: T11 QA-2); charging allocated bytes as instructions (deterministic, but table.sort, table.insert shifting, string.find scans and long string compares allocate nothing); reading the clock on every event (the read costs more than many calls it guards); reading it only on count events (up to 1000 instructions of heavy calls run between reads). Still open: a single C library call such as backtracking string.find, `string.rep("", 1e15)` or `table.move({}, 1, 1e12, 1, {})` can run for minutes with no hook event, and a looping `<close>` handler run by `lua_closethread` after the budget ends a `coroutine.wrap` body runs with hooks off for good (T11 QA-5; docs/DEBT.md); only a console in a Worker that the page can terminate would bound them.
