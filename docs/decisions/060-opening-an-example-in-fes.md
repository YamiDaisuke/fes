# 060 Opening an example in FES
Status: accepted (2026-11-19, T56)
Context: The manual's examples are complete carts (decisions 057, 058). A reader inside the Help view should be able to open one without retyping it. The manual is a same-origin iframe, the parent page is the app, and SPEC keeps JS from owning cart state.
Decision: Every data-example group in the manual, the API entries' examples and the Examples alike, gets an Open in FES key after its last pre, added by manual.js only when the page is inside a frame. Its accessible name is "Open <heading> in FES", the heading being the h3 of the pre's section. The key posts { fesExample: name } to window.parent with the manual's own origin as the target. web/boot.js ignores the message unless its origin is the app's and fesExample is a string. It doesn't check event.source: WebKit gives the parent window, not the iframe's, as the source of a message posted from a module script such as manual.js, and any same-origin sender could change the app anyway. It then reads the matching pres from the Help iframe's live DOM, comparing dataset.example in JS rather than building a selector, and passes the heading and a list of { file, text } (file defaults to main.lua) to globalThis.fesOpenExample, a closure App sets at boot. Swift treats both as untrusted. The name must pass nameProblem. The files go through Cart.replaceCodeFiles(with:), which wants exactly one main.lua, puts every other file through addCodeFile (name rules, duplicates, the 32-file limit) and caps the total at Cart.largestArchiveBytes. The cart is checked before the unsaved-changes question, so the question is never asked for an example that then fails. The opened cart is demoCart() with the example's name and code, so it has the demo's art, including sprite tile 1. It opens with no folder, like New cart: Save makes a new cart, an untouched example counts as unchanged (the manual still has it), and its recovery copy restores as a new cart. Opening shows the Code view. Cancel leaves the cart and the Help view as they were.
Alternatives: keys only on the six Examples (a section filter, and the API examples are tested carts too); checking event.source against the iframe's window (WebKit rejects every real key press, see above); JS validating names (JS would own a cart rule); passing a files dictionary through Cart(files:) (round-trips the art through text, and hides duplicate names); opening on newCart() (blank art, so the sprites are invisible); posting the example's text in the message (a second copy of the text, and trusting the sender's text instead of the app's own DOM).
