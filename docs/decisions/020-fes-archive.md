# 020 .fes archive, export and import
Status: accepted (2026-11-05, T15b)
Context: Decision 013 shares a cart as a zip of its folder named <cart name>.fes. SPEC puts zip export and import in Storage, no zip library is approved, and an imported file is untrusted input. In a Home Screen web app, <a download> strands the user on an "Open in…" screen (WebKit bug 290847), and iPadOS can't register a .fes type.
Decision: Storage writes and reads store-only zips (method 0, no zip64, encryption or data descriptors) by hand, with one CRC-32 shared with the golden PNG writer. Export writes the six cart files at the top level in Cart.fileNames order, dated 1980-01-01 so the bytes are reproducible without Foundation. Import refuses files over 8 MiB (the Lua memory cap) before reading them, then refuses archives without an exact end record, multi-disk, over 64 entries, encrypted, compressed, out of range, with a CRC mismatch or duplicate names. Entry names are only compared with Cart.fileNames, never used as paths; other entries are ignored as 013 ignores unknown files. Known files must be strict UTF-8, then Cart(files:) validates as for OPFS. An imported cart always goes into a new folder with its name unchanged and is not opened; the open cart is never touched. Export uses the editor's code and the name field, names the file <name>.fes with characters Files rejects replaced by -, and hands it to navigator.share in a Home Screen app and to <a download> in a tab. The import picker has no accept filter.
Alternatives: a zip library (new dependency for about 120 lines); deflate (an inflater in Swift); CompressionStream in JS (format logic in JS); renaming duplicates on import (breaks an exact round trip and differs from Save); replacing a same-named cart (silent data loss); <a download> everywhere (dead end in a Home Screen app); accept=".fes" (iPadOS may grey out unknown types).
