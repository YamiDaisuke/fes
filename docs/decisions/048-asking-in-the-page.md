# 048 Asking in the page
Status: accepted (2026-11-16, T45)
Context: FES asked with the browser's confirm and prompt (039, 041), which can't be styled and look out of place in the installed app. They also blocked the event loop, and some guarantees silently depended on that: nothing could replace the open cart, press a console button or start other storage work while a question was open. An in-page dialog is asynchronous, so those guarantees must be kept on purpose.
Decision: One <dialog id="ask"> in index.html, a .plate .dialog whose title strip is the question and its accessible name, with an optional text field, a Cancel key and a confirm key. Swift's ask(_:confirm:cancel:textField:destructive:) shows it with showModal and awaits its close event through a continuation. It returns nil for Cancel or Escape, and otherwise the field's text ("" without a field). ask is only called from inside afterEarlierStorageWork. That queue keeps two questions from sharing the dialog, and keeps loads, imports, deletes and saves from changing the cart between a question and the action it guards; so New file, Rename, Delete file and the sheet import now wait for earlier storage work. While the dialog is open the page is inert, and keys typed inside any dialog are page keys: they never reach the console or the Art view's undo shortcut. Delete still removes a cart only after a yes, with nothing awaited between the answer and the removal, and reads whether the cart is open after the answer. A destructive confirm is a coral key, and focus starts on Cancel, so Enter cancels. Otherwise focus starts on the field or the confirm key, and Enter in the field confirms. Declining the Restore question discards the recovery copy, so its cancel key says Discard and focus starts on Restore. On close, the dialog itself returns focus to the element focused when the question opened. The dialog sits near the top, so the iPad keyboard doesn't cover the field, with its left edge rounded down to a whole --u (045).
Amends: 039 (names and deletes are asked in the page), 041 (the confirm is awaited inside the queue).
Alternatives: a promise per question from JavaScriptKit or a JS helper (more machinery than one continuation; JS would hold the answer); a queue of questions inside ask with re-checks in every caller after the answer (two mechanisms, and each caller must notice that the cart changed); answering Cancel when the dialog is busy (would decline the Restore offer unasked and drop the recovery copy); centring with margin: auto (lands on half pixels on odd window widths, and the iPad keyboard hides the field); separate confirm and prompt functions (two entry points for one dialog).
