# 042 Cart label
Status: accepted (2026-11-16, T39)
Context: M11's shelf (docs/PHASE2.md) shows each cart as a cartridge with a picture, like PICO-8's label, captured from the running game. The picture is cart data, so it joins the permanent format (013) and reaches Storage from OPFS, .fes archives and the recovery copy, all untrusted.
Decision: A cart may hold label.hex, a 192×144 picture as 144 lines of 384 hex digits, two per pixel, each a main palette index 00–3f; written lowercase with a final newline, read in either case, with 013's and 034's text rules (LF or CRLF, one leading byte order mark dropped, a lone CR refused). Indices rather than RGB keep it 55,440 bytes and let the label follow the cart's main palette. The file is optional in every format: a cart without it has no label; one that is malformed refuses the cart naming the file, line and character column, as every cart file does. cart.json moves to format 4: every cart saved from now on is format 4, with or without a label, so an older FES refuses it rather than dropping a label on save; formats 1–3 load unchanged. label.hex is in Cart.fixedFileNames (the non-code files a cart may hold) and in cart.fileNames only when the cart has a label, after map.map, so export, import, duplicate and the recovery copy carry it with no code of their own, and a .fes entry that would unzip as it is refused (020). "Set label" in the game view captures the last frame drawn: each pixel becomes the index of the equal color in the running cart's main palette (the one the frame was drawn with), or of the nearest by the sum of squared channel differences, the lower index winning ties and duplicates so a captured label round-trips. Setting a label is an edit: the cart becomes unsaved and the recovery copy is rewritten. Nothing removes a label yet, so a save never deletes label.hex; a future "remove label" must delete it on save, as 036 does for code files.
Amends: 013 (cart files and format number), 020 (archive entries read), 025 (the copy grows by about 55,600 characters with a label, about 2 % of the quota).
Alternatives: keeping format 3 because older FES ignores unknown files (it would drop the label on its next save, which 013 rejects); RGB per pixel (three times larger, and the label would not follow palette edits); a PNG file (binary in a text-based cart, and needs a decoder at a trust boundary); ignoring a malformed label as decoration (the next save would drop it silently); capturing with the cart's main palette instead of the running one (differs once the game view can be shown without restarting, T43).
