# 005 Native stacked pull requests
Status: accepted (2026-10-30, owner request after #18 merged into a dead base)
Context: Tasks stack so building never waits on review. With plain PRs, each child's base is its parent's branch, and the orchestrator retargets children after a merge. When the owner merged #17 and then #18 four minutes later, #18 still targeted `t01-scaffold`. T02's code landed in that branch instead of `main`, and had to be re-landed through #21. GitHub now has native stacked PRs. Cloud sessions can't install the `gh stack` CLI: the proxy blocks the release download, and the CLI looks PRs up through GraphQL, which is blocked. The Stacks REST API (`repos/{owner}/{repo}/stacks`) does work through the proxy; stack 22 was created that way.
Decision: Every open task PR is a layer in one native stack, managed with `gh api` calls to the Stacks REST API. The branches and the git rebases stay as they were. GitHub merges a layer only together with every unmerged layer below it, and retargets the layers above, so a layer can't land in a dead parent branch. "Automatically delete head branches" goes on: nothing needs a merged branch any more, and this session's proxy can't delete branches.
Alternatives: The `gh stack` CLI doesn't run in cloud sessions (see Context); it's fine for the owner on their own machine. Keeping manual stacks with auto-delete on would make GitHub retarget children, but a child could still be merged before its parent.
