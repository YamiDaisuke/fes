# 011 Console API v0
Status: accepted (2026-10-31, T10)
Context: SPEC names cls, spr, btn, btnp, mget, mset and camera but leaves their signatures to this task. The PPU is a sprite table over a tilemap (decisions 006, 008), not a framebuffer, so PICO-8's draw-now calls need a meaning here. Every argument comes from cart code, a trust boundary where a Swift trap (Int(Double.nan), Int(1e300)) would kill the app and unsaved work.
Decision: The API writes hardware state; the PPU renders after _draw. spr(n, x, y, [palette], [flip_x], [flip_y], [behind]) fills the next free sprite table entry in call order, so the frame's first spr is in front (decision 008); once all 64 are in use, further calls do nothing. cls() empties the table and starts again at entry 0. Otherwise the table keeps its sprites from frame to frame, as PICO-8's screen keeps pixels until cls. cls never touches the tilemap and takes no color. camera([x, y]) sets the background scroll and the offset every later spr subtracts, so map and sprites share world coordinates as with PICO-8's camera; sprite positions in the PPU stay in screen pixels (decision 008). The background uses the camera in effect when the frame renders, a sprite the camera in effect when spr ran, so camera() for a HUD also scrolls the map to 0, 0 until the window layer (M4); the owner accepted this for v0, and HUD sprites are drawn at the camera position plus their screen offset. mset(x, y, tile, [palette]) and mget(x, y) -> tile, palette address the 32x32 background tilemap in cells and wrap like the PPU (decision 006); palette defaults to 0. btn(i)/btnp(i) take Button numbers 0-7 (decision 009) and return false outside them. On the keyboard A (4) and B (5) follow PICO-8's keys, Z and X, by owner decision; this reversed T08's original key map in decision 009. Number arguments go through luaL_checknumber (numbers and numeric strings; anything else raises "main.lua:N: bad argument #k to 'name' (number expected, got T)"). NaN and inf raise "finite number expected", except in btn/btnp, which return false for them like any other number outside 0-7. Finite values are floored, as PICO-8 floors positions, then wrapped modulo 65536 in Double, a multiple of every field width, before conversion to Int; the Console types then mask as in decision 004. Flip and priority must be boolean or nil, because Lua treats 0 as true. Extra arguments are ignored. Each binding is a top-level Swift function used as a lua_CFunction, pushed with lua_pushcclosure and one upvalue: the RunningCart as unretained light userdata, safe because the cart's deinit closes the lua_State. luaL_check* errors longjmp through the binding's Swift frame to the cart's lua_pcall (decision 010), skipping Swift releases. So a binding reads every argument into plain values before it fetches the cart or creates anything that needs releasing, and nothing after that point raises. Error texts reach C as StaticString pointers, because an implicit String-to-C conversion allocates at -Onone and the longjmp skips its release.
Alternatives: spr drawing into the framebuffer (a second, non-hardware path without the sprite limits); spr(slot, ...) addressing entries like NES OAM (every cart manages slots); clearing the table before each _draw (cls would do nothing; sprites set in _init could not stay); camera offsetting only sprites (map and sprites drift apart) or only scrolling (spr after camera lands in the wrong place); mget returning 0 off the map like PICO-8 (disagrees with the wrapped background); errors for out-of-range tiles, palettes and cells (decision 004 wraps); luaL_checkinteger (rejects 1.5, so fractional speeds need math.floor); Lua truthiness for flips; btn wrapping its index (btn(8) would mean left); a capturing Swift closure (cannot be a C function pointer).
