# 009 Input
Status: accepted (2026-10-31, T08)
Context: SPEC gives input gathering to JS and input state to Swift, as one button bitmask per frame, but fixes no bit order, key map, touch model or repeat rule, and iPad Safari adds multi-touch, implicit pointer capture, cancelled touches and lost key-ups.
Decision: frame(heldButtons:) takes the mask as its wasm argument; bit order is Swift's Button order (left, right, up, down, A, B, Start, Select = bits 0–7, PICO-8's numbers for the first six), mirrored in web/input.js. JS sends every button held at frame time OR'd with any pressed since the last frame, so a tap shorter than a frame lasts one frame. Swift's Input keeps this and last frame's mask: isHeld backs btn, wasPressedThisFrame backs btnp, true only on the first held frame, with no auto-repeat. Keys by event.code: arrows, Z = A, X = B (PICO-8's keys; T08 had them the other way round until the owner swapped them in T10, decision 011), Enter = Start, Shift = Select; mapped keys preventDefault. Touch uses Pointer Events: pointerdown on the overlay tracks a pointer, each move sets its buttons to the control under it (elementFromPoint, data-buttons), pointerup/pointercancel release it, and window blur releases every key and pointer. The D-pad is a 3×3 grid whose corners are diagonals. The overlay sets touch-action, user-select and -webkit-touch-callout to none.
Alternatives: a separate setButtons export (a second call to keep in order); edge detection in JS (JS would own console state); Touch Events (non-passive listeners, a separate mouse path, not constructible in desktop WebKit tests); per-button pointerenter/leave (touch pointers are captured to the first button, so slides never leave it); PICO-8's btnp auto-repeat (PLAN defines btnp as pressed this frame; revisit in T10 if carts need it); event.key (layout dependent).
