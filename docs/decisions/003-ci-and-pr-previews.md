# 003 CI and PR previews
Status: accepted (2026-10-25, T03)
Context: Every PR needs a preview at /pr/<number>/ next to main at the Pages root, so the owner can try each PR on the iPad. With the "GitHub Actions" Pages source, each deploy replaces the whole site.
Decision: A gh-pages branch stores the site; only CI writes it. After tests pass, scripts/publish-pages.sh rewrites one folder (/ keeping pr/, or pr/<n>/) and force-pushes the result as a single parentless commit with --force-with-lease, retrying if another publish won the race; a single commit keeps 9 MB wasm builds from piling up in history. A deploy job in a "pages" concurrency group then uploads the whole branch with actions/upload-pages-artifact and actions/deploy-pages; a newer deploy may cancel a pending one safely because it uploads the newer tree. Closing a PR removes its folder; the next deploy drops it from the site. The github-pages environment must allow all branches to deploy through a "Selected branches and tags" rule `*`; with "No restriction" Pages only accepts deployments from main. The repo is public so Pages works without a paid plan, which makes the site and every preview public to anyone with the URL. CI uses only GitHub's own actions/* and installs the toolchain with scripts/setup.sh. It caches .build keyed on setup.sh and Package.resolved.
Alternatives: Pages source "Deploy from a branch" (GITHUB_TOKEN pushes don't trigger Pages builds, and branch builds are limited to about 10 per hour); rebuilding main plus every open PR per deploy (several cold wasm builds or expiring artifacts); deploying only from main via workflow_run (no preview until the workflow is on main); third-party preview actions (unapproved dependencies); a private repo on a paid plan (the owner chose public on issue #3).
