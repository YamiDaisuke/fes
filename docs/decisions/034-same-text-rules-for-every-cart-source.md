# 034 The same text rules for every way a cart arrives
Status: accepted (2026-11-14, T28)
Context: A cart's files reach Storage from OPFS, from a .fes archive and from the recovery copy. OPFS reads went through a TextDecoder that silently dropped a leading UTF-8 byte order mark (since T13), while Cart(fesArchive:) passed it on and the parsers refused it, so the same cart loaded from one source and was "damaged" from another (issue #64). Text editors reached from the Files app on iPadOS, and Notepad on Windows, add that mark, and the user can't see it. Separately, a lone CR in a grid file was reported as a wrong line count on the last line, with the raw CR in the message (issue #37, QA-5).
Decision: One leading U+FEFF is dropped from every cart file's text, in Swift only: Cart(files:) drops it as it takes each file (Storage/TextLines.swift's withoutByteOrderMark), so OPFS, .fes and the recovery copy share the rule. web/storage.js readCartFile decodes with ignoreBOM: true, which in the Encoding standard means "keep the mark in the text", so JavaScript no longer decides. The cart list reads cart.json alone through parseCartJSON, so it drops the mark with the same function. The mark is not kept: saving writes the files without it. A second mark, or one anywhere else, is ordinary text: the strict files refuse it, and main.lua keeps one inside the code. One left at the very start of main.lua stays in memory, where Lua refuses it on Run, but is lost when the code is shown in the editor or saved, because JavaScriptKit's string bridge decodes every Swift string with a TextDecoder that drops a leading mark. In the grid files (tile sheets, main palette, palettes, map), textLines refuses the first line holding a CR that is not part of a CRLF, naming that line and writing the character as \r, before it checks the line count. This amends 013 ("reads LF or CRLF") and 020 ("Known files must be strict UTF-8, then Cart(files:) validates as for OPFS"): both now also accept one leading byte order mark.
Alternatives: refusing the mark from both sources (a cart edited in a common editor becomes damaged for an invisible byte); stripping in JavaScript and in Cart(fesArchive:) separately (two copies of the rule, and the recovery copy a third); stripping every U+FEFF (inside main.lua it may be part of a string the cart wrote on purpose); accepting a lone CR as a line break (013 chose LF or CRLF only, and no current editor writes it).
