# 004 Palettes and tile memory
Status: accepted (2026-10-30, T04)
Context: SPEC fixes the hardware numbers (64-color master palette, 8 background + 8 sprite palettes of 8 colors, 256 background + 256 sprite tiles of 8×8 at 3 bits per pixel, sprite color 0 transparent) but not how tile pixels are stored, what palettes hold before a cart sets them, or what happens with an out-of-range index.
Decision: TileBank stores each tile row as one UInt32 with pixel x in bits (7 - x) * 3 to +2 (pixel 0 highest); row y of tile t is element t * 8 + y. The layout is private to TileBank and is not a file format; the cart format (T12) is separate. PaletteBank holds 64 master indices, entry palette * 8 + index, defaulting to entry n = master color n so the eight palettes spread the whole master palette. Every index wraps to its field width with a bit mask (tile & 0xFF, x/y/palette/index/pixel color & 0b111, master index & 0x3F), so negative or large values never trap; the Lua API and cart parser validate at their own boundaries. Color 0 is ordinary in these types; sprite transparency is the sprite renderer's rule. The master palette is a generated placeholder (2 bits per channel, levels 0/85/170/255) until the owner picks one in M3.
Alternatives: NES/Game Boy-style bitplanes (3 bytes per row; three shifts per pixel, only useful if raw bytes are ever exposed, and SPEC defaults to no peek/poke); one byte per pixel (no decoding, but 3bpp would only be a mask); traps on bad indices (a trap in wasm kills the app and unsaved editor work); throwing or optional lookups (error handling at every render call for input that is already validated upstream); all-black default palettes (every scene needs setup and a missing one is invisible).
