# 051 The Art view's pixel colors
Status: accepted (2026-11-17, T48a)
Context: Swift draws the tile sheet, the edit area and the import report into canvases, so their grid, tile borders, selection ring and transparent checker can't be CSS. They were placeholder greys and white (DEBT). M12's look (045) wants them in its tokens, and the owner, a pixel artist, needs the art's own colours to read true.
Decision: Grid lines are --shell-deep, the edit area's tile borders --ink, and the transparent checker --shell-light and --shell-dark like the transparent swatch. The selection (sheet block and edit-area cursor) is a 2-pixel ring: --ink on the grid line, --butter one pixel inside it, so one of the two always shows against the grid and against any art; it covers the selected tile's edge pixels in the sheet (a third of them at zoom 3), which the edit area shows whole. The import report's problem ring stays #ff3030, because the report keeps its old look. The six token colours are constants in Editors/ArtPixel.swift that mirror web/style.css by hand; web/tests/art-look.spec.js compares the drawn pixels with the computed tokens, so retuning a token means changing ArtPixel.swift and re-recording the goldens (006). Canvas pixels are opaque, and nothing on the Art canvases or their ancestors may use filter, opacity or mix-blend-mode; a screenshot test checks that an art pixel reaches the screen unchanged.
Alternatives: reading the tokens from CSS at run time and passing them to Swift (bridge code and colour parsing for six values that change only when the owner retunes); a one-colour ring (vanishes on art of its own colour); a ring outside the selection (covers the neighbouring tiles instead); a sunken well around each canvas (costs the 201u sheet area its spare pixel, so zoom 3 would drop at 744 px, decision 050).
