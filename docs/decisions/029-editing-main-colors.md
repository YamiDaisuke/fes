# 029 Editing main colors
Status: accepted (2026-11-13, T22)
Context: PLAN's T22 changes the selected main color with the iPadOS color picker, an <input type="color"> (owner, PR #51), so every palette entry using it changes too, and resets the cart's main palette to the default (decision 021). Decision 028 makes the main color assigned to the selected entry the aria-pressed one. In WebKit on iPadOS, every color the picker reports, including each step of a continuous drag, sets the input's value and fires input and then change (WKFormColorControl.mm, ColorInputType::didChooseColor). Closing the popover fires no event and, on iPad, doesn't blur the input (WKContentViewInteraction.mm blurs only on small screens). The picker has no Cancel. Not yet checked on an iPad.
Decision: The palette panel has a labelled <input type="color">, "Edit main color n", which edits the main color assigned to the selected entry and is disabled while sprite color 0 is selected. Swift listens to its input event only. It reads the value with Color(hexCode:), which accepts # and 6 ASCII hex digits in either case and refuses anything else, leaving the cart unchanged and saying so in the cart status. Each accepted value is the edit: it sets cart.mainPalette at once and redraws at most once per animation frame (023), so the sheet, the entries and Run show it while the picker is still open. Closing the picker keeps the last color. Each accepted value also writes the recovery copy (025) at once, because a drag has no end event, so a reload, a closed tab or a tab iPadOS freezes or kills right after a value keeps it. That costs a median of 1.4 ms (worst 2.4 ms) per value with a 64 KB main.lua and 1.0 ms (worst 1.6 ms) with the demo cart, against under 0.1 ms without the write; each sample is the average of 20 values in a row, over three runs of 50 in Playwright's WebKit on a 4-core 2.1 GHz cloud VM; not yet timed on an iPad. UIKit reports touches at most once per display frame, so a drag should give at most 120 values a second on a ProMotion iPad, about 17 % of each 8.3 ms frame, unlike Pencil's 240 coalesced points a second that 025 keeps off the copy. "Reset main palette" asks with confirm (no undo before T23), puts back Z64, keeps each entry's main color number, writes the recovery copy, and is disabled while the palette is already Z64. Save, Export and the recovery copy write main-palette.hex through Cart.files as before (021).
Alternatives: committing on change (WebKit fires it on every step) or on blur (never fires on iPad); a separate main color selection (028 rejected a second selection); a hidden input opened with showPicker() from a JS module (more code, and a hidden control VoiceOver could reach); writing the copy 500 ms after the last value (round 1: a reload, a closed tab or a killed tab within 500 ms lost the edit); that debounce plus a write on pagehide and on visibilitychange to hidden (more code, and a frozen tab still can't run it); Reset without a confirm (up to 64 custom colors lost with one tap and no undo).
Later: decision 030 makes a picker session one undo step and drops Reset's confirm.
