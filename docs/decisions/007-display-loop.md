# 007 Display loop
Status: accepted (2026-10-30, T06)
Context: SPEC gives the frame loop and the blit to JS and all state to Swift. The 192×144 RGBA framebuffer (decision 006) lives in wasm memory and must reach a Canvas 2D every frame, and a browser test needs a deterministic frame to compare.
Decision: App exports `frame()` as a raw wasm export (`@_expose(wasm, "frame") @c`). Each call renders the next frame of the current scene and returns the address of Framebuffer.rgba. boot.js calls it from requestAnimationFrame and wraps the bytes in place: a Uint8ClampedArray over instance.exports.memory.buffer, an ImageData, then putImageData. The view is rebuilt every frame because memory growth detaches the old buffer, and the address is only valid until the next Swift call. Swift owns the frame counter, and one rAF callback is one console frame, with no wall-time pacing. The browser test stubs requestAnimationFrame, runs a fixed number of frames, and compares the canvas's getImageData with the native golden PNG for that frame, so native and browser share one reference image recorded with FES_RECORD_GOLDENS=1 swift test.
Alternatives: BridgeJS @JS exports (experimental, needs a build plugin); a JSClosure on a JS global (a JavaScriptKit round trip per frame); copying the pixels through JavaScriptKit (110 KB plus a JS object per frame); a fixed-timestep accumulator (no consumer yet, see docs/DEBT.md); Playwright toHaveScreenshot (a second, platform-named reference set that depends on the device scale factor; a scaled screenshot was checked to be exact but adds decoding for no extra coverage); a frame-count URL parameter in boot.js (test logic in product code).
