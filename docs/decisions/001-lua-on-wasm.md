# 001 Lua on wasm
Status: accepted (2026-10-25, T02)
Context: Lua raises errors with setjmp/longjmp. WASI has no native setjmp; the Swift 6.4.1 Wasm SDK's setjmp.h refuses to compile without wasm exception handling, and the result must run in Safari on iPad.
Decision: Vendor Lua 5.4.9 unmodified (lua.org tarball, sha256 2335b6c582a52654f94612bf10d2f4672805d05329aa6568b1d8cd9e5c6fb8e6) as the CLua C target. On wasi, compile it with -mllvm -wasm-enable-sjlj and link the SDK's libsetjmp; clang 21 lowers setjmp/longjmp to legacy wasm exception handling (try/catch/throw), supported since Safari 15.2. Verified in Playwright WebKit 27.2: pcall catches errors from Lua, from coroutines and from a Swift closure registered as a C function. Only the sandbox's libraries are vendored: lua.c, luac.c, linit.c, liolib.c, loslib.c, loadlib.c and ldblib.c are left out, so io, os, package and debug are not in the binary. _WASI_EMULATED_SIGNAL and _WASI_EMULATED_PROCESS_CLOCKS satisfy lstate.h and ltablib.c; Swift's static link already links both emulation libraries.
Alternatives: compiling Lua as C++ so errors are C++ exceptions (needs the same wasm feature plus libc++abi with exceptions); the newer exnref encoding (Safari 18.4+, no gain today; revisit if browsers drop legacy EH); Asyncify (Binaryen not approved, slows every call); Lua 5.5 (SPEC says 5.4).
