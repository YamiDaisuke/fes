# 006 Background layer and golden images
Status: accepted (2026-10-30, T05)
Context: T05 needs a framebuffer format, a tilemap size and scroll rules that SPEC doesn't fix (map dimensions are an open decision for M4), plus PNG golden tests without a compression library: Foundation on Linux has no zlib API, and system zlib would be a new dependency.
Decision: Framebuffer is [UInt8] RGBA, row-major from the top-left, alpha 255: canvas ImageData's layout. The background tilemap is 32×32 cells (256×256 px), provisional until the owner decides map sizes in M4; it must stay a power of two because wrapping is a mask. A cell is a tile (0–255) and a background palette (0–7), masked on write like decision 004. scrollX/scrollY are the map pixel shown at screen (0, 0) and wrap modulo 256, negatives included. Golden tests encode the frame as a PNG with uncompressed (stored) deflate blocks and hand-written CRC-32/Adler-32 in the test target, and compare the bytes with Tests/ConsoleTests/Golden/<name>.png; a mismatch writes <name>.actual.png beside it; FES_RECORD_GOLDENS=1 swift test re-records (and fails, so record mode never passes silently). Goldens use the placeholder master palette and must be re-recorded when the owner picks the real one.
Alternatives: packed [UInt32] pixels (byte order depends on endianness); a configurable map size (configuration with one real value); system zlib through a system-library target (new dependency, extra CI package); a PNG decoder to compare pixels (about 40 more lines for a nicer failure message; the encoder is deterministic, so byte equality is pixel equality); SwiftPM resources for the goldens (#filePath finds them without Bundle.module).
